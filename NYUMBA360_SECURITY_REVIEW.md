# Nyumba 360 Cybersecurity Review

**Review date:** 24 August 2026  
**Review method:** Static review of the TypeScript/React/Express/tRPC/Drizzle codebase, a live response-header check, a production dependency audit, and limited safe configuration checks. This was **not** an intrusive penetration test and no live accounts, secrets, customer data, payment providers, or database records were accessed.

## Executive summary

> The application has a solid starting point in several places: authenticated and administrator-only tRPC guards exist, important listing updates check ownership, the document-vault download route checks authorization, environment files are ignored, and no obvious hard-coded key signatures were detected in tracked source. The review nevertheless found several material gaps that should be corrected before the platform carries more sensitive documents, payments, or high traffic.

The highest priorities are to patch vulnerable dependencies, prevent public access to pending/rejected listings and seller PII, close the unauthenticated object-storage retrieval path for private documents, harden uploads, and introduce rate limiting. The report distinguishes confirmed code findings from framework/dependency advisories whose exploitability still depends on runtime paths.

## Preliminary confirmed findings

| ID | Priority | Plain-English issue | Evidence | Recommended correction |
|---|---:|---|---|---|
| SEC-01 | **Critical** | The production dependency tree contains one critical and many high-severity published advisories. The most important direct packages include `@trpc/server` 11.6.0, `axios` 1.12.2, `drizzle-orm` 0.44.6, Express/path-to-regexp, `nanoid`, and transitive AWS SDK, Mermaid, DOMPurify, and markdown-rendering packages. | `package.json`; installed dependency inventory; `pnpm audit --prod`. | Upgrade direct dependencies deliberately, regenerate the lockfile, run the full test/build suite, then re-run the audit. Do not use a blind force upgrade; validate breaking changes in staging. |
| SEC-02 | **High** | Public property detail, photo, and seller procedures return raw database records without first enforcing that the property is approved or projecting only public fields. Someone who guesses a numeric listing ID may be able to view pending/rejected listing details, exact coordinates, internal owner IDs, and seller account data such as email, phone, and `openId`. | `server/routers.ts:604-619`; `server/db.ts:144-149`, `194-199`; `drizzle/schema.ts:17-30`, `36-75`. | Create explicit `getPublicPropertyById`, `getPublicPropertyPhotos`, and `getPublicSellerProfile` query projections. Require `status === "approved"` for anonymous callers; allow owners/admins through separate protected procedures. Never return `openId`, email, full phone number, role, timestamps, or raw database objects publicly. |
| SEC-03 | **High** | The storage proxy turns any requested `/manus-storage/<key>` into a signed download URL without authentication or ownership checks. This undermines the private document-vault route if a document key becomes visible in an API response, browser history, logs, screenshots, or a shared link. | `server/_core/storageProxy.ts:4-47`; protected document download in `server/routers.ts:1856-1865`. | Remove the universal public storage proxy for private prefixes. Permit only deliberately public prefixes through a tightly allowlisted public route. Keep private documents behind the existing authorized download procedure, return short-lived signed URLs only after checking access, and omit `fileKey` from client-facing private-document responses. |
| SEC-04 | **High** | Several upload paths trust a user-supplied filename and MIME type and do not enforce a server-side file-size cap, file count, content signature, or safe type allowlist. A signed-in attacker can consume memory/storage, upload active content labelled as an image, or use crafted files against downstream viewers. | `server/routers.ts:560-569`, `1178-1196`, `1502-1529`, `1624-1639`; global 50 MB parsers in `server/_core/index.ts:34-36`. | Apply a shared upload policy: small per-route body caps; strict MIME and extension allowlists; magic-byte/content checks; generated server filenames; per-user/property quotas and rate limits; image re-encoding; malware/CDR scanning for office documents; and force download / no-sniff headers for untrusted downloads. |
| SEC-05 | **High** | No application-level rate limiting or anti-automation controls were found. Public inquiries can be spammed, public nearby-POI calls can spend Maps quota, property views can be inflated, and authenticated upload/AI endpoints can be abused for cost or resource exhaustion. | `server/_core/index.ts:31-66`; public inquiry mutation at `server/routers.ts:945-977`; public Maps endpoint at `server/routers.ts:488-520`; AI/upload routes. | Add layered limits at the edge and app: IP + account limits, endpoint-specific quotas, payload limits, `429` responses, abuse logging, and CAPTCHA/turnstile on public inquiries. Treat Maps and LLM calls as cost-bearing endpoints with tight limits. |
| SEC-06 | **Medium–High** | A long-lived session JWT is mirrored into JavaScript-readable `sessionStorage` and accepted as a reusable Bearer token. If an XSS bug or malicious browser extension reads that storage, the token can be taken and used away from the browser. The normal HttpOnly cookie benefit is weakened. | `client/src/main.tsx:45-69`; `server/_core/sdk.ts:166-197`, `258-277`. | Restrict the preview fallback to non-production environments, or replace it with a short-lived, audience-bound, one-time token. Prefer HttpOnly cookies only; shorten session lifetime; rotate tokens; add server-side revocation (`jti`) and reauthentication for sensitive actions. |
| SEC-07 | **Medium** | Session cookies use `SameSite=None`, and the API accepts cookie-authenticated state changes without an explicit CSRF control. This is needed only for genuinely cross-site flows and widens cross-site request exposure. | `server/_core/cookies.ts:42-47`; protected mutation surface in `server/routers.ts`. | Use `SameSite=Lax` or `Strict` in production where the OAuth flow allows it. If `None` is truly required, implement a CSRF token/origin-validation strategy for state-changing requests and test OAuth callback compatibility. |
| SEC-08 | **Medium** | Baseline input validation exists through Zod, but important lists and strings remain unbounded. Examples include public inquiry fields, property input arrays, user preference arrays, and property pagination. Combined with the 50 MB global parser, this permits avoidable memory, database, and storage pressure. | `server/routers.ts:576-590`, `621-649`, `945-953`; `server/routers.ts:137-151`; `server/_core/index.ts:34-36`. | Add `.max()` to all text and array inputs, positive caps to pagination, maximum image/video counts at the API boundary, and substantially smaller route-specific request limits. Reject oversize requests with `413`. |
| SEC-09 | **Medium** | The app does not set a complete security-header policy itself. The live platform supplies HSTS, `X-Content-Type-Options`, and no-store caching, but exposes `X-Powered-By: Express`; no CSP, frame-ancestors/X-Frame-Options, Referrer-Policy, or Permissions-Policy were observed in the live headers. | `server/_core/index.ts:31-66`; live header check on 24 Aug 2026. | Disable Express fingerprinting and set hardened headers using a carefully configured middleware or hosting policy. Roll out CSP first in report-only mode because Google Fonts and analytics need approved sources. |
| SEC-10 | **Medium** | Untrusted assistant content is rendered as Markdown while the dependency tree has markdown/Mermaid/DOMPurify advisories. This creates a wider XSS/CSS-injection blast radius if raw HTML or diagram features are enabled now or later. | `client/src/components/AIChatBox.tsx:263-270`; `package.json`; dependency audit. | Update the rendering stack, keep raw HTML disabled, disable or tightly configure Mermaid for untrusted content, and add regression tests with hostile Markdown/URL payloads. A CSP is a helpful additional control, not a substitute for safe rendering. |
| SEC-11 | **Low–Medium** | Security-relevant activity is partially audited for advanced modules, but authentication failures, public inquiry abuse, upload rejects, rate-limit events, and suspicious document/proxy access do not have a clear structured security-event trail. | `server/_core/context.ts:11-28`; `server/_core/storageProxy.ts:17-46`; router audit-log usage. | Add structured, redacted security telemetry with retention/alerting: authentication failures, CSRF/origin failures, upload rejections, quota hits, document-download decisions, and administrator actions. Never write tokens, full PII, or file contents to logs. |

## What is already positive

The code uses shared `protectedProcedure` and `adminProcedure` guards, and many sensitive owner actions verify record ownership before mutation. The document-vault download route is a useful model: it checks owner/uploader/grant/admin permission before generating a signed URL. Environment files are ignored by Git, and a source-signature scan found no obvious committed API-key or private-key markers. These controls should be preserved while the weaker paths are repaired.

## Remediation update — immediate priority items completed

The authorized immediate remediation was implemented after this review. Public marketplace procedures now return explicit approved-listing projections instead of raw records, and anonymous seller results are limited to a display name and profile image. Pending and rejected listings remain visible only to their owner or an administrator; private seller email, phone, open ID, role, listing owner ID, and raw listing status are no longer in the anonymous response contract. The public property page now directs visitors to the secure inquiry flow instead of publishing seller contact details.

The storage proxy now permits only explicitly public asset prefixes and branded root assets. `property-documents/` and other private keys receive a generic not-found response, while the existing authorized document-download procedure remains the path for short-lived signed document downloads. Security regression tests cover anonymous approved-only access, owner-only draft access, seller-field projection, hidden private photos, and the storage allowlist.

The production dependency set was upgraded, including tRPC, Axios, Drizzle, Express 4, NanoID, AWS SDK packages, Streamdown, and the remaining Lodash resolutions. The final production audit reported **0 critical** and **0 high** advisories, with **one moderate** advisory still requiring separate follow-up. The application passed TypeScript, all 33 test files / 153 tests, and the production build after the remediation.

## Practical repair order

| When | What to do | Simple outcome | Verification standard |
|---|---|---|---|
| **Immediately** | Upgrade and lock dependencies; re-run `pnpm audit --prod`; patch the public listing/seller projections; disable the public proxy for private storage keys. | Attackers cannot browse non-public listings, retrieve private documents by object key, or exploit known package defects as easily. | Production audit has no critical/high findings without documented compensating controls; security tests prove pending/rejected listings and seller PII are unavailable anonymously. |
| **Next 7 days** | Introduce shared upload validation, narrow request limits, rate limits, public-inquiry abuse controls, and Maps/LLM quotas. | A normal account or anonymous bot cannot cheaply fill storage, overload the server, flood inquiries, or consume paid APIs. | Automated tests reject too-large, wrong-type, spoofed, and over-quota uploads; load tests receive `413`/`429` rather than server failure. |
| **Next 14 days** | Remove production bearer-token mirroring; shorten/revoke sessions; add CSRF/origin protection; deploy security headers in report-only mode. | A script injection has much less chance of turning into an account takeover, and cross-site state changes are constrained. | Browser tests cover login, logout, OAuth callback, expired/revoked session, and rejected cross-origin mutations. |
| **Before payments or wider document use** | Conduct a staged authenticated penetration test, review cloud/S3 IAM and CORS settings, add malware scanning/content-disposition controls, and exercise incident response. | Real payment and document workflows have assurance beyond code review. | Independent test report shows the fixes working and critical/high findings are closed or formally risk-accepted. |

## Important limits of this review

This assessment reviews the application repository and the observed live response headers. It cannot confirm cloud IAM policies, object-bucket ACLs, WAF configuration, OAuth provider settings, platform-managed secrets, database encryption/backups, historical logs, or whether a vulnerability has already been exploited. Those must be reviewed separately with appropriately authorized access. The report also does **not** claim to prove that no other issue exists; security testing is iterative and should continue after each major release.
